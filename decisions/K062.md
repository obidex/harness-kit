## K062 · 2026-11-22 · STANDING — a failed settings apply is that repository's alert; only that repository's green apply closes it

**Found (22 Nov 2026, the owner's card for it).** `hands-settings` failed on its schedule two days running
on one project's apply: GitHub refused (422) a new ruleset whose bypass actor was the GitHub Actions
integration, which GitHub does not accept on a repository a personal account owns. The run's one alert,
`hands/hands-settings`, was then closed "green again" by a run started by hand that applied another
repository only. The project's apply was never green; the branch stayed unprotected while the alert
read as solved.

**Decision.**
1. Each `hands-settings` apply job records its repository and result (`result.txt` beside its log).
   `hands-report` keeps one alert per repository, key `hands/<job>/<owner/name>`: a failed apply opens
   it, and only that repository's own green apply closes it. A green apply of another repository
   changes nothing.
2. A run that failed outside the repository jobs (the drift check) is the job's own alert,
   `hands/<job>`, as before; a green apply never closes it, a full check with nothing to apply does.
3. The drift check lists each repository that matches its file (`HANDS_MATCHED_FILE`); its apply alert
   closes there too, so a repository put right without an apply is not left with an open alert. A
   paused repository is never listed.
4. `hands-update` and `hands-keep` record no per-repository result and keep their one alert.

**Why.** An alert closes on evidence about the thing that failed, not on a green run of something else.

Homes: `templates/hands/hands-settings.yml`, `templates/hands/hands-report.yml`, `tools/hands.mjs`
(drift), `hands.md`; checks in `tools/test-hands.mjs` and `tools/test-notify.mjs`.

**Status:** STANDING.
