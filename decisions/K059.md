## K059 · 2026-11-21 · CI speed: a chore lane, one scrub run per burst, checks scaled to the change with a nightly full run, the long test job split

**Owner (21 Nov 2026, Platform thread).** Seeing about thirty runs queued, he asked how to make the runs
faster without lowering quality, and approved the proposal: "a separate line for chores, one chore run
per burst, checks scaled to the change with a full run every night, the long test job split, and the
two runs stuck since 11 Nov cancelled. No required check is removed or weakened, and nothing is paid."

**Context.** Measured that day: 92 runs waiting across five repositories, about 11 of them real tests;
51 were `harness-scrub`, which started one run per comment (its group was keyed on the comment). A scrub
works 6 to 25 seconds and waited 5 to 38 minutes behind test jobs of 13 to 24 minutes on the same
single runner. 5,346 workflow runs started in 24 hours. GitHub-hosted minutes that month: about 1,200
of the plan's 3,000 counted (the billing page), the largest share from a private repository whose
chores run GitHub-hosted.

**Decision.**
1. **Chore lane.** Every short kit job runs on `vars.CHORE_RUNNER || vars.RUNNER || 'ubuntu-latest'`;
   the long `harness-sweep` stays on `RUNNER`. A chore runner registers with only the chore label
   (`--no-default-labels`), so it takes nothing else. A public repository sets neither (A19, which now
   checks `CHORE_RUNNER` too).
2. **One scrub run per burst.** One concurrency group per repository (one running, one waiting; GitHub
   drops older waiting runs). Each run sweeps every body updated since the newest earlier green run,
   less 5 minutes and never more than a day, so a dropped run's body is still cleaned. A read-only event
   (a fork's or Dependabot's pull request) keeps its own group and sweeps nothing.
3. **Checks scaled to the change.** `scope.mjs decide` says light (documents only, outside the paths a
   build may read) or full (anything else, every push, the nightly run, any doubt), plus whether a path
   is tier 3. A workflow without a nightly schedule is never light. The required check is one gate job
   (`scope.mjs gate`) that passes only when every needed job passed, or was skipped on a light run. Both
   run from the base branch. The rule is tested (`tools/test-scope.mjs`). Projects adopt it in their own
   CI from `ci.md`.
4. **Split the long test job** (`ci.md` §4): a test runner's sharding or one job per suite, with runner
   processes to run them side by side where a machine has room. Project CI, adopted by each project.
5. **No required check is removed or weakened.** A light run still runs the secret scan, the guards
   and lint; the gate replaces per-job required checks only in the same settings change.

**Not done here.** The runs left queued by GitHub on 11 Nov (no jobs) could not be cancelled: the API
answered 409 to cancel and force-cancel and 403 to delete (I102, I103 in the infra project), and
GitHub's own run page answers "Failed to cancel workflow" (21 Nov). They hold no runner. Only GitHub
Support could remove them.
