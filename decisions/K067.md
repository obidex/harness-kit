## K067 · 2026-11-25 · STANDING — the audit's C17 lost-lines test honours the baseline's known commits

**Asked.** A project's inbox request (filed on the owner's board, found at kit 0.48.1): after the kit's own
prescribed correction (`decisions.md`, "Switching a project": an entry appended to the closed log moves
into its own file), `audit.mjs` C17 failed for good. Its lost-lines test reads the log's last 50 commits,
the move removes lines, and a closed log never gains 50 newer commits. History is never rewritten, putting
the entry back fails the decisions check, and accepting all of C17 in the baseline would also hide the
caps, the always-loaded budget, the decisions check and "a written decision file was edited".

**Decision.**
1. **Known commits, as A10 and O09.** C17's lost-lines test skips exactly the commits the baseline lists for
   C17 (`{ "id": "C17", "commits": [...], "why": ... }`, SHAs of 7+ characters, short or full) and says how
   many it skipped. Any other commit that removes a line still FAILs.
2. **Only that test.** The caps, the load budget, the decisions register, the "never edited" test and the
   generated references are never skipped; a `commits` entry is never a whole accepted rule in `--strict`
   (as before).
3. **Why not recognise the move by itself.** Matching removed lines against a new `decisions/<ID>.md` in
   the same commit would pass, with no person's judgment, any removal whose text reappears in a file, and
   would need its own rules for whitespace, partial moves and renames. A baseline line is narrower: one named
   commit, a written `why`, reviewed on the project's pull request, and reusing code the audit already
   trusts for A10 and O09.

**Record.** `.harness/tools/audit.mjs` (C17; the C17 diff now reads full SHAs so a full or short baseline SHA
matches); `.harness/audit/README.md` "The baseline"; `.harness/decisions.md` "Switching a project";
checks in `tools/test-decisions.mjs`.

**Status:** STANDING.
