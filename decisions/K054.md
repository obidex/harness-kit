## K054 · 2026-11-20 · STANDING — a second reviewer reads every pull request, paid from an API credit, with no key

**Owner (20 Nov 2026, project chat).** His bulk paste asked for a plan to use his plan's monthly API
credit for a second reviewer on every pull request: "plan only, no key", with a spend limit equal to the
credit. The plan went to him the same day; he signed in to the API console so the limit could be set, and
the build was started as a card.

**Context.** C10's fresh-context reviewer reads tier-3 and profile-risky diffs. Everything else merged on
its checks alone. O07 already has a seat for optional reviewers: asked once, never waited on, each finding
given an outcome.

**Decision.**
1. **One kit workflow, `harness-review.yml`, with its tool `review.mjs`** (`review.md`). When a
   pull-request workflow finishes green and every check on the head commit is green, one job asks a
   model C10's question about the diff and keeps one comment on the pull request.
2. **Advisory, always.** Never a required check, never an approval, never in place of C10. A project
   must not add it to `branches.required_checks` or to a ruleset.
3. **Models.** Sonnet by default, Opus on high-risk paths (the profile's `risk.tier3_paths`, workflows
   and agent configuration everywhere). Haiku never reviews (O06). The ids and prices are constants in
   the tool: a model changes by a kit release, never by a variable.
4. **No key.** Workload identity federation only; the four identifiers are Actions variables, and the
   workflow is inert until the rule's variable is set. The federation rule pins the workflow file, the
   default branch, the event and the repository's ID. The kit never reads or stores a key for this.
5. **The pull request is data.** `workflow_run` only (never `pull_request_target`, A19), nothing of
   the pull request is checked out or run, the model's input is tagged as data, and its answer is
   posted as text. A fork's pull request and a bot's are never sent to the model.
6. **Caps in code, per repository and UTC day:** $1 and 40 reviews, one review per commit, 5 minutes a
   run; variables may only lower them. The plan named $2.50 a day across all repositories; a job can
   count only its own repository, so the cap is per repository and lower, and the reviews workspace's
   spend limit is the stop across repositories. Over a cap or out of credit: one line, merges go on.
7. **The runner** is the project's `RUNNER` lane like every kit workflow. The access token lasts
   minutes, is limited to the reviews workspace, and stays in the job's memory; the job runs no pull
   request code. A project that kept credit jobs off its own machines for an older, wider token may now
   run this one there.
8. **The kit reviews itself** with a copy of the template in its own `.github/workflows`, kept equal
   by `test-review`.

**Not decided here.** Whether a project drops another paid reviewer for this one: that waits for a
side-by-side run on past pull requests with known bugs, and is that project's decision.

Homes: `tools/review.mjs`; `templates/workflows/harness-review.yml`; `review.md`; `test-review`.

**Status:** STANDING.
