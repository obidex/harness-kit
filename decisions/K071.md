## K071 · 2026-11-26 · STANDING — closing a request is part of finishing it; "answered, not closed" is counted

**Asked.** A strategist request on the owner's board (26 Nov 2026), asks 4 and 5: the Control Center's Work
page showed 57 open inbox requests, about 22 of them already finished or answered but never closed.
Technical, kit-internal work; no money, no design. Approval recorded as not checked (the request came
through the strategist); it changes no request's content and no approval.

**What was found.** `inbox.mjs state --to done` already closes a request, but threads often answered on
the issue with a DONE note and never ran it, and requests filed without an inbox-id line (strategist cards)
cannot be closed by the tool at all. Nothing counted such a request, so it stayed open as "queued" or
"working" on every count.

**Decided.**
1. The thread that answers a request closes it in the same step as its DONE line: `state --to done`, or by
   hand with the same evidence for an issue with no inbox-id. One left open after DONE is a papercut (C28).
   The line lives where the inbox rule lives (`inbox.md`, "The issue", and the `inbox` skill's step 4);
   no always-loaded text changes.
2. `metrics.mjs` counts "answered, not closed": an open `inbox` issue whose State line says `done`, or whose
   newest comment that no bot wrote has a line opening with `DONE` (C03). It is the smaller of the two
   places offered (the metrics already read every open issue for stalls; the papercut digest reads only
   papercut issues). At most 60 requests are read per repository; more is named as partial.

**Not taken.** Closing requests automatically from the metric: a DONE line can be partial ("DONE —
part 1"), so the count is a list for the thread or coordinator, never an action.

**Prevention.** `tools/test-metrics.mjs` (cases for the DONE line, the State line, a bot line after DONE,
newer work after DONE, a card that is not a request, the Markdown column, an unreadable repository).
