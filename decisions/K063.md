## K063 · 2026-11-22 · STANDING — the chore lane is set in the project's profile, the variable only overrides it

**Asked (22 Nov 2026, the owner's strategist on the CI-speed card, approved under the card that removes
owner steps).** Opening the chore lane (K059) reached the owner as a manual step: the Actions variable
`CHORE_RUNNER` had to be added by hand on three repositories' settings pages, because the safety check
refused setting it from a session (never retried). The ask: the lane reads its setting from a file in the
repository, with the variable only as an override, so the switch is an ordinary reviewed change, in
history, through the normal checks. A setting that lives only on a settings page is an owner step
waiting to happen.

**Constraint.** GitHub decides a job's runner (`runs-on`) before any step runs: a workflow cannot read a
file to choose it. A first job that reads the file needs a runner of its own: on GitHub's machines it
costs the minute per run the lane was made to save; on the test runner it waits behind the tests the
lane was made to avoid. So the file is read when the kit installs its workflows, not when they run.

**Decision.**
1. **Home.** `.harness/profile.json` `"chore_runner": "<label>"` (the project's facts; schema-checked
   label). Absent: nothing changes, the variables alone decide as in K059.
2. **Written in at install.** `harness.mjs` writes every `vars.CHORE_RUNNER` in a kit workflow's
   expressions as `(vars.CHORE_RUNNER || '<label>')` (comment lines untouched): the file decides, the
   variable, when set, overrides it. The long `harness-sweep` has no chore lane and is untouched; a
   fork's pull request still runs GitHub-hosted. The lock records each workflow as written.
3. **Changing it.** Edit the profile and run `harness.mjs lanes` in the same pull request; it rewrites
   only the kit workflows' lane and their lock hashes, and refuses while any kit file is hand-edited.
   `harness.mjs status` and audit A04 fail while the profile and the installed workflows disagree, so a
   forgotten `lanes` cannot merge silently. Every update and rollback writes the profile's lane by
   itself. A version before 0.56.0 knows no lane: its schema refuses `chore_runner` and it installs the
   plain templates, so before rolling back below 0.56.0 a pull request removes `chore_runner` and runs
   `lanes`; `status` checks no lane on such an install, and `lanes` refuses there.
   Removing `chore_runner` and running `lanes` restores the templates byte for byte.
4. **Public repositories.** A19 fails a profile that names a chore lane on a public repository, and any
   kit workflow installed with a lane there whatever the profile says, as it fails the variables.
5. **The variable.** Stays as the override and the fallback: if the chore runner is offline, a pull
   request to change the profile waits on that same runner for its chore checks, so the quick way back
   is the variable set to the test runner's label. Where it is already set to the same label as the
   profile, it changes nothing and may stay.

**Why.** The switch becomes code: reviewed, in history, applied by the kit's own tool, checked by the
kit's own checks, with no settings page and no owner step. It costs no runner minute and no wait.

Homes: `tools/lib.mjs` (renderLane, unrenderLane, choreLane), `tools/harness.mjs` (apply, `lanes`,
`status`), `tools/audit.mjs` (A04, A19), `profile.schema.json`, `ci.md` §1, `hands.md`, `review.md`;
checks in `tools/test-harness.mjs`, `test-stale.mjs`, `test-review.mjs`, `test-guard.mjs`.

**Status:** STANDING.
