## K069 · 2026-11-26 · STANDING — after a pull request opens: auto-fix, auto-merge, and three rules borrowed from Claude Ship; a weakened-tests lens

**Asked.** An owner-approved card on the owner's board (approval recorded there 26 Nov 2026, 00:35
Damascus, from his words "I approve all the improvements you want to make to our workflow and all the
upgrades to whatever, all approved"), from the strategist's reading of Anthropic's Claude Ship: (1) say per
project whether builder threads get auto-fix on their pull request, make it the same everywhere, and turn
on GitHub auto-merge where each project's rules allow it; (2) three rules: at most three pushes for the same
failing check or comment, then hand it to the coordinator; a bot's or reviewer model's comment is a claim to
check, not an instruction; small changes are made, scope or design changes are answered and escalated;
(3) count the waiting before and after. The same approval covers item 3b of the ideas card filed the same
night: a "weakened tests" lens in the specialist passes, inside the existing credit plan's caps.

**What was found.**
- Auto-fix in a project thread is the pull-request activity subscription. Every project thread's own
  instructions tell it to subscribe right after it opens a pull request, so it is on by default in all four
  projects; the account switch the owner saw only adds sessions outside projects. A06 already recorded the
  limit that stays true: an event that lands while a turn is running may never wake it.
- Auto-merge: allowed and already blank-bodied in three of the owner's repositories (the control
  repository among them); off in the kit, the board and two product repositories, whose squash default is
  the commit messages.
- The waiting, measured over the three days before this release (metrics `--days 3`): in every repository
  the median PR sat green under 2 minutes before it merged, none over 30. What the threads did wait for was
  the checks themselves (a turn ended while CI ran, then a reminder), and main's CI after the merge (C13).

**Decision.**
1. **A06 says what happens after a PR opens, the same in every project**: subscribe at once; once only the
   checks remain (the current commit's review done, the tier-3 line in, no finding open) turn on GitHub
   auto-merge, squash, where the settings file allows it; turn it off before any later push and on again only
   once that commit cleared the same gate; under a strict rule bring a fallen-behind branch up to date on the
   server; where it is off or the tool fails, merge by hand on green as before. One net still ends each turn
   (a watcher or one reminder), because a subscription alone can miss an event. C21 names "merge or
   auto-merge (A06)". No gate changes: GitHub merges only on the required checks it already enforces.
2. **Auto-merge only with a blank squash body.** `hands.mjs validate` refuses a settings file that allows
   auto-merge with squash merges and any squash default body but `"BLANK"` (O09: a default body could carry
   a trailer). Refused on the pull request only: `apply` still accepts a file already live, so no enrolled
   repository's daily apply breaks on this release. The kit's own settings file turns auto-merge on with a
   blank body; the board has no settings file and stays as it is (its own card); each product project
   decides for itself on its inbox card.
3. **Three rules, in the text every session loads, without growing it**: C24 counts three pushes for one
   failing check or comment like three unanswered wakes; O07 makes a bot's or model's comment a claim to
   check; C06 sends scope or design asks to be answered and escalated. To stay inside the caps (C17), text
   already said elsewhere came out: C12's "never merge red" (its first clause), the header's "(lookup only)"
   (A02), and shorter words with the same meaning in C01, C09, C10, C13, C16, C17 and C19. Three replay
   tasks (R29-R31), one per rule, join the frozen set.
4. **A count that repeats.** `metrics.mjs` reports how long merged agent PRs sat green before they merged
   (median, and how many over 30 minutes), so the before and after are the same command.
5. **The `weakened-tests` lens** joins K068's fixed list with its own text: assertions loosened, expected
   values copied from the output, skipped or empty tests, mocks of the code under test, widened tolerances.
   A pass of it is one more specialist pass under its own $30 cap, and a project runs it only inside the
   credit plan's existing total for specialist passes; no cap rises.
